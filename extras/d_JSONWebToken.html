El problema del Login tradicional

La clase pasada logramos que el usuario se autentique (validamos su contraseña hasheada). Pero, ¿qué pasa cuando quiere hacer una acción protegida, como borrar un usuario?

Si no hacemos nada, cualquiera podría hacer un DELETE a la API sin estar logueado. Y si le pedimos que mande su contraseña en cada petición, estaríamos exponiendo sus datos constantemente.

❌ Sin Token

La API está abierta. Cualquiera con Postman puede borrar la base de datos.

❌ Mandar la pass siempre

Inseguro y molesto. El usuario tendría que escribirla en cada clic.

¿Qué es un JWT? (La Pulsera VIP)

JWT (JSON Web Token) es un "pase digital". Una vez que entrás al sistema, el servidor te da un token único. En cada petición, mostrás ese token en vez de tu contraseña.

🎟️ Analogía: Imaginate un boliche. En la puerta (el Login) mostrás tu DNI (la contraseña). El patovica (el backend) te da una pulsera VIP (el Token). Para entrar a la pista principal (las rutas protegidas), no volvés a mostrar tu DNI, solo mostrás la pulsera. El patovica de la pista solo mira que la pulsera sea original y no esté vencida.
¿Qué tiene adentro un Token? (La estructura)

Un JWT es un string separado por 3 puntos. No es magia, es solo texto codificado.

El flujo del Token

  1. 1 El usuario manda email y pass al /login.
  2. 2 El backend valida la pass. Si es correcta, genera el token con jwt.sign().
  3. 3 El frontend recibe el token y lo guarda en el localStorage.
  4. 4 En cada petición protegida (ej. borrar), el front envía el token en el Header: Authorization: Bearer <token>.
  5. 5 El backend verifica el token con jwt.verify(). Si es válido, deja pasar la acción.

El Código Paso a Paso

A. Generar el Token (Controller Login)
import jwt from 'jsonwebtoken'; // ... const payload = { id: usuario.id, email: usuario.email }; const token = jwt.sign(payload, process.env.JWT_SECRET, { expiresIn: '2h' }); res.json({ mensaje: 'Bienvenido', token: token });
B. El Middleware Guardián (Nuevo archivo)
// middlewares/auth.middleware.js export const verificarToken = (req, res, next) => { const authHeader = req.headers['authorization']; const token = authHeader && authHeader.split(' ')[1]; if (!token) return res.status(401).json({ error: 'Falta el token' }); try { const verificado = jwt.verify(token, process.env.JWT_SECRET); req.usuario = verificado; next(); // Pasa a la ruta } catch (error) { return res.status(403).json({ error: 'Token inválido o vencido' }); } };

JWT: Pros y Contras

✅ PROS ❌ CONTRAS
⚡ Súper rápido: el servidor no tiene que buscar la sesión en la base de datos, solo verifica la firma. 🚫 Una vez emitido, no se puede revocar fácilmente (si lo roban, sirve hasta que venza).
📦 Autocontenido: el token ya lleva los datos del usuario adentro (id, email). 📦 Más pesado que una sesión tradicional (viaja en cada header).
🌐 Ideal para APIs y apps móviles (funciona en cualquier lenguaje). 💾 Si lo guardás en localStorage, es vulnerable a ataques XSS (robo por scripts).

El mundo real (y qué haremos después)

El estándar de la industria hoy en día no es usar localStorage para guardar el token. Si un hacker logra inyectar un script (XSS), puede robarse el token y hacerse pasar por tu usuario.

La solución pro: Guardar el token en Cookies HttpOnly. Son cookies que JavaScript no puede leer (evita el XSS), pero el navegador las envía automáticamente al backend.
